# Keyless vault file format

**Status: Gate 0 format proposal — freeze only after cryptographic review and implementation tests. No vault implementation exists in this repository yet.**

## 1. Design choices

- Container version: v1.
- Authenticated encryption: XChaCha20-Poly1305 only.
- Passphrase KDF: Argon2id v=19 (0x13).
- Key separation: HKDF-SHA-256 with distinct, versioned context strings.
- Serialization of the encrypted payload: UTF-8 JSON Canonicalization Scheme (RFC 8785).
- One authenticated encrypted snapshot contains the complete logical record set. This intentionally hides record names, count and types from an offline observer and makes passphrase changes and atomic replacement straightforward. Records have a stable logical layout described below; they are not separate ciphertexts in v1.

No custom cryptography is permitted. Use maintained implementations and have the selected libraries reviewed before implementation.

## 2. Binary container layout

All integers are unsigned big-endian. The fixed header is exactly 72 bytes.

| Offset | Length | Field | V1 value / meaning |
|---:|---:|---|---|
| 0 | 8 | Magic | ASCII bytes `KEYLESSV` |
| 8 | 2 | Format version | `1` |
| 10 | 2 | Flags | `0`; unknown bits are rejected |
| 12 | 1 | KDF ID | `1` = Argon2id v=19 |
| 13 | 4 | Argon2 memory | KiB; bounded before KDF runs |
| 17 | 4 | Argon2 iterations | Bounded before KDF runs |
| 21 | 2 | Argon2 parallelism | V1 requires exactly `4` |
| 23 | 16 | KDF salt | Fresh CSPRNG salt |
| 39 | 1 | AEAD ID | `1` = XChaCha20-Poly1305 |
| 40 | 24 | AEAD nonce | Fresh random nonce for every vault write |
| 64 | 8 | Ciphertext length | Includes the 16-byte Poly1305 tag |

The file is the 72-byte header followed by exactly `ciphertextLength` bytes. The ciphertext is the AEAD ciphertext concatenated with its 16-byte authentication tag. No trailing bytes are allowed.

Reject truncated headers, impossible lengths, files above the v1 64 MiB container cap, unknown IDs, unsupported flags, and malformed headers before allocating large buffers or running the KDF.

## 3. Argon2id parameters

Argon2id parameters are stored in the header and checked against hard bounds **before** running Argon2id. Values outside the supported range are refused; the implementation must not clamp them.

| Parameter | V1 default | Minimum accepted | Maximum accepted |
|---|---:|---:|---:|
| Memory | 65,536 KiB (64 MiB) | 65,536 KiB | 1,048,576 KiB (1 GiB) |
| Iterations | 3 | 3 | 10 |
| Parallelism | 4 | 4 | 4 |
| Salt | 16 bytes | 16 bytes | 16 bytes |
| Derived master key | 32 bytes | 32 bytes | 32 bytes |

- Argon2 version is fixed to 19 (0x13).
- Memory must satisfy the Argon2 minimum relation to parallelism and be a multiple of 4 KiB.
- The KDF runs asynchronously in a worker thread or maintained native worker pool. It must not block the daemon event loop.
- The default is a floor, not a benchmark claim. Gate 2 must measure unlock latency on supported hardware before format freeze; any changed default requires a format note and review.
- Passphrases are UTF-8, not trimmed or silently normalized. Reject NUL. Require at least 12 Unicode code points and recommend a long, unique passphrase (for example, four or more randomly selected words). Never store or log the passphrase.

The maximum bounds are denial-of-service protections for hostile/tampered headers. They are not a recommendation to use the maximum values.

## 4. Key derivation and AEAD

1. Derive a 32-byte master key with Argon2id v=19 from the passphrase, header salt and stored bounded parameters.
2. Derive the vault-state AEAD subkey with HKDF-SHA-256:
   - input key material: Argon2id master key;
   - salt: the 16-byte KDF salt from the header;
   - info: ASCII `keyless/v1/vault-state`;
   - output length: 32 bytes.
3. Authenticate and decrypt the payload with XChaCha20-Poly1305 using the header bytes (all 72 bytes) as associated data.
4. Derive any future purpose-specific keys from the master key with unique, versioned HKDF info strings. Never reuse the vault-state key for audit integrity, backup encryption or unrelated purposes.

The 24-byte XChaCha nonce is generated by the OS CSPRNG for every successful write. A nonce is never reused with the same subkey. Rewriting the complete snapshot naturally creates a new nonce. No deterministic or counter-based nonce scheme is used.

The complete fixed header—including format version, KDF identifier, all KDF parameters, salt, cipher identifier, nonce and ciphertext length—is AEAD associated data. Modifying a KDF parameter or version must cause authentication failure after a bounded KDF attempt. Parameter floors/ceilings are checked first to prevent attacker-controlled resource exhaustion.

## 5. Encrypted payload and logical record layout

The decrypted plaintext is UTF-8 JSON in RFC 8785 canonical form:

```json
{
  "schemaVersion": 1,
  "vaultId": "base64url-encoded-16-byte-id",
  "generation": 12,
  "records": [
    {
      "recordId": "uuid",
      "kind": "credential",
      "recordVersion": 1,
      "revision": 3,
      "createdAt": "2026-11-05T00:00:00.000Z",
      "updatedAt": "2026-11-05T00:00:00.000Z",
      "data": {
        "alias": "openai",
        "provider": "openai",
        "secretBase64url": "<encrypted-payload-only-value>"
      }
    }
  ]
}
```

Logical record kinds in v1:

- **credential:** alias, provider ID and credential bytes encoded as base64url. Do not store provider secrets in plaintext in metadata or sidecar files.
- **project:** random project ID, canonical path digest, project creation time and identity revision.
- **grant:** project ID, alias, normalized provider/method/path/query/model rules, transport caps, revision, approval timestamp and approval hash.
- **project-token:** project ID, token ID, SHA-256 digest of the 256-bit random token, issue time, expiry and revocation state. The plaintext token is not stored in the vault payload.

Every record has a UUID record ID, kind, record version, monotonically increasing revision and UTC timestamps. Unknown record kinds or record versions are rejected. Unknown fields are rejected for v1 records. The payload schema is separate from the outer container version.

All logical records are encrypted together inside the single snapshot ciphertext. This is deliberate: an observer should not learn aliases or the number of credentials from record framing. Per-record AEAD is not used in v1. The vault ID is inside the encrypted payload; the unique per-write nonce and header salt provide the outer cryptographic context.

Reject duplicate record IDs, duplicate credential aliases within a project/provider namespace, invalid timestamps, unsafe integers, invalid base64url, missing mandatory records and inconsistent project/grant/token references.

## 6. Wrong passphrase and corruption behavior

An AEAD authentication failure cannot reliably distinguish a wrong passphrase from tampering or ciphertext corruption. Return one non-leaky error such as:

```text
Unable to authenticate the vault. The passphrase may be incorrect or the vault may be damaged.
```

Do not reveal credential aliases, record counts, project IDs or which record failed. Structural errors detected before decryption may be reported as an invalid or unsupported vault file, without dumping bytes or header data to logs.

Never attempt a lower KDF parameter set as a recovery fallback.

## 7. Atomic writes and file locking

- Keep the vault under the user's Keyless state directory, never in the project repository.
- Create the directory owner-only (0700 POSIX) and the vault file owner read/write only (0600 POSIX); use owner-only DACLs on Windows.
- Acquire an OS-backed exclusive lock for the vault before reading-modifying-writing. A PID file alone is not a lock. Use a maintained cross-platform lock primitive; stale-lock recovery must verify process identity and must not delete a live lock based only on age.
- Serialize the new complete payload, derive a fresh nonce, encrypt it, and write a temporary file in the same directory using exclusive creation and restrictive permissions.
- Flush the temporary file to stable storage, close it, atomically replace the vault, and flush the parent directory where supported.
- Keep the old vault intact if serialization, encryption, write, flush or replacement fails. On startup, ignore incomplete temp files and do not promote them automatically.
- Concurrent writers are serialized by the OS lock. A daemon crash during a write must leave either the old complete vault or the new complete vault, never a partially written file.
- Do not log temp paths if they contain sensitive user directory information.

The exact lock and atomic-replace primitives are platform implementation decisions, but the invariants above are mandatory on macOS, Linux and Windows.

## 8. Newer formats and migration

- If the magic is valid but the format version is greater than the implementation supports, refuse to open it and tell the user to upgrade Keyless.
- If the version is lower and a reviewed migrator exists, migrate only after successful authentication and write the new file atomically. Keep a recoverable backup according to the backup policy.
- Never guess a schema, silently downgrade, or rewrite an unknown version.
- A migration failure leaves the original file unchanged.

## 9. Master passphrase change: `keyless passwd`

1. Require an unlocked vault and a fresh hidden prompt for the old passphrase; re-authenticate before changing.
2. Prompt for the new passphrase twice and validate the v1 minimum.
3. Decrypt the current snapshot in memory, generate a fresh 16-byte salt and 24-byte nonce, and use the current approved KDF profile (default unless a later profile is reviewed).
4. Re-encrypt the complete payload with the new derived key and new authenticated header.
5. Atomically replace the vault under the exclusive lock.
6. Only after durable replacement, discard the old in-memory key material as best the runtime permits and keep the session in the documented unlocked state using the new key.
7. Record a metadata-only passphrase-change audit event; never log either passphrase or derived key.
8. If any step fails before replacement, the old vault and old passphrase remain valid.

Changing the passphrase does not change provider credentials, grants or project tokens. Token rotation and credential rotation are separate operations.

## 10. Backup boundary

Backups and portable export/restore are not defined by this container format. Do not copy a live vault while it is being rewritten. Gate 2 must define a separately versioned encrypted backup envelope, its independent passphrase KDF, restore behavior and policy for restoring revoked tokens before production implementation.
